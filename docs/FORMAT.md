# CULDCEPT.DAT 포맷 (컬드셉트 리볼트, 3DS)

아래는 전부 게임에서 직접 리버스 엔지니어링한 내용입니다(공식 문서 없음).
오프셋·핸들러 주소는 압축 해제된 ARM 실행 파일(ExeFS `.code`, 디스크에서는 BLZ 압축됨)
기준입니다.

## 1. 아카이브 컨테이너

```
오프셋 0:  레코드 테이블 -- 8바이트 엔트리 N개:
             u32 LE  offset      (파일 내 위치)
             u32 LE  size        (이 엔트리의 바이트 수)
           N = table[0].offset / 8   (데이터는 테이블 바로 뒤에서 시작)
엔트리 i:  DAT[offset : offset+size]
```

엔트리 첫 바이트가 코덱 타입입니다. 관측된 타입: `0x08`, `0x0c`, `0x0d`, `0x8d`(압축);
`0x00`(원시/중첩 컨테이너, 24비트 빅엔디언 오프셋 테이블 사용); `0x05`(원시 CWAV 오디오).

엔트리 크기를 바꾸려면 새 바이트를 **파일 끝에 추가**하고 해당 8바이트 레코드만 갱신하면
됩니다 — 다른 엔트리의 오프셋은 그대로 유지됩니다.

## 2. 코덱 디스패치

단일 디스패처(guest `0x27f3f4`)가 타입 바이트를 읽어 핸들러 테이블(`0x39bb58`,
`type & 0x3f`로 인덱싱) + 후처리기(`0x39bb90`, `type >> 6`로 인덱싱)를 선택합니다:

| 타입 | 핸들러 | 방식 |
|------|--------|------|
| 0x08 | 0x274b90 | canonical Huffman + LZ (윈도우 0x0d) |
| 0x0c | 0x274b88 | canonical Huffman + LZ (윈도우 0x10) |
| 0x0d | 0x275080 | LZMA 계열 레인지 코더 |
| 0x8d | 0x275080 | 동일 레인지 코더, 후처리기만 다름 |

## 3. 타입 0x08 / 0x0c — Huffman + LZ (`culdcept/huffman.py`에 구현)

```
entry = [type u8] [varint size] [비트스트림]
```

- **size**는 연속 비트(continuation-bit) **varint**(핸들러 `0x2747f8`)이며, `size>>8`이
  **아닙니다**. 아카이브 레코드의 size 필드와 이 varint는 겹치는 바이트에서 읽히지만,
  실제 압축 해제 길이는 varint입니다.
- **비트 리더**(`0x275020/0x275028`): 32비트 누산기에 대해 MSB 우선. 리필은 little-endian
  `u16`을 읽어 바이트를 뒤집어 누산기 상위에 넣습니다. varint 뒤 `pos`가 홀수면 1바이트를
  미리 로드하고, `consume(16)`으로 프라이밍. 결과적으로 `pos`부터의 엔트리 바이트에 대한
  단순 MSB 우선 비트스트림입니다.
- **블록**을 `size` 바이트가 나올 때까지 반복:
  - `r8 = getbits(16)` — 블록 내 심볼 수.
  - **litlen** 테이블(`0x274d18`): 19심볼 코드길이(CL) 테이블을
    `read_lengths_direct(19, 5, special_pos=3)`으로 읽고, `count = getbits(9)`개의 코드
    길이를 CL로 RLE 디코딩(`s>2 → 길이 s-2`, `s==0 → 0`, `s==1 → 3+getbits(4)`개의 0,
    `s==2 → 0x14+getbits(9)`개의 0).
  - **dist** 테이블: `read_lengths_direct(window+1, (window+1-10)&5, -1)`.
  - `r8`개 심볼: `sym<0x100`이면 리터럴; 아니면 `length=sym-0xFD`, 거리 코드
    `dsym → dd = (dsym==0?1:(1<<(dsym-1))+1+getbits(dsym-1))`, 매치 복사.
- **`read_lengths_direct(nsym,nbits,special)`**: `count=getbits(nbits)`; 0이면 단일 심볼
  `= getbits(nbits)`. 아니면 길이마다: 상위 3비트 `t`; `t<7 → 길이 t`(3비트 소비) 아니면
  `길이 = 7 + clz32(~(acc<<3))`(길이-3 소비). `i==special`에서 `r=getbits(2)`; `r>0`이면
  `r`개의 0을 건너뜀.

최소 유효 인코더는 블록마다 `r8`, degenerate CL 테이블(단일 심볼 10 → 0비트), `count=256`
(256개 전부 길이 8 → 리터럴 바이트 B가 그대로 8비트 값 B), degenerate dist 테이블, 그리고
원시 리터럴 바이트를 씁니다. `compress()` 참고.

## 4. 비트맵 폰트 (압축 해제된 리소스, `culdcept/font.py`)

```
오프셋 0x30: CMAP -- u16 LE 문자 코드; glyph_index i -> CMAP[i].
             ASCII 0x20-0x7e, 반각 0xa1-0xdf, Shift-JIS 0x8140+, 가이지 0xf9xx.
크기 섹션 헤더(8바이트): 14 00 | bpg(u16) | b4 | w | h | bpp
```

4bpp 텍스트 크기(`bpp==4`, `b4==0xCE`)의 경우 글리프 비트맵은 `섹션 + 0xCE`에서 시작하며,
글리프 `i`는 고정 `w×h` **A4**(4비트 알파, 상위 니블 우선) 셀로 `bpg = ceil(w/2)*h` 바이트,
위치는 `섹션 + 0xCE + i*bpg`입니다.
탑재 크기: **10px**(bpg 50), **12px**(bpg 72), **14px**(bpg 98).
12×12 16bpp "아웃라인" 섹션(`b4==0x10`, `bpg 288`)도 있지만 글리프가 ~160개뿐(한자 없음)
이라 본문 텍스트에는 쓰이지 않습니다.

게임은 Shift-JIS를 CMAP으로 글리프 인덱스로 변환한 뒤 글리프를 A4 텍스처에 그려서 텍스트를
렌더링합니다. 렌더링 파이프라인은 Azahar LayeredFS로 실기 확인했습니다.

## 5. 시나리오 컨테이너 (스토리 대사, `culdcept/scen.py`)

스토리 대사는 코덱으로 압축된 최상위 엔트리에 **없습니다**. 대사는 자체 헤더로 시작하는
**시나리오 컨테이너** 엔트리에 있습니다. 이 엔트리의 첫 바이트는 코덱 타입이 아니라 헤더
크기의 최하위 바이트라서(관측값 `0x30`/`0x48`/`0x68`/`0x80`/`0xa8`/`0xb0`/`0xe0` 등), 코덱
타입만 보는 스캐너는 이 엔트리를 통째로 지나치게 됩니다.

```
dword0 (u32 LE) = 헤더 크기(바이트).  헤더 = (섹션 offset u32, 섹션 length u32) 쌍 배열.
                  섹션 개수 = dword0 / 8.
섹션 k          = entry[offset : offset+length].  대부분 0x08(간혹 0x0c) 압축.
```

한 스테이지의 컨테이너에는 여러 섹션이 있고, 그중 하나가 **대사 스크립트**입니다
(압축 해제 후):

```
[스크립트 바이트코드 / 헤더]  그 다음  [텍스트 영역]
```

- **텍스트 영역**은 null(0x00) 종료 "이벤트"의 연속이고, 각 이벤트는 `0x07`로 나뉜
  "페이지"(대화창 하나)들로 이루어집니다.
- **제어 코드**: `0x00`=이벤트 끝, `0x07`=페이지 넘김(클릭 대기), `0x0a`=줄바꿈,
  `0x03 0x30 0x2f`=플레이어 이름 삽입.
- 이벤트는 내부에 `0x00`을 포함하지 않으므로, 섹션을 null로 분할했을 때 **마지막 N개
  세그먼트가 곧 N개 이벤트**입니다 — 이렇게 텍스트 시작을 확실히 찾습니다.
- ★**게임은 각 페이지/이벤트의 시작을 텍스트 영역 내 절대 바이트 오프셋으로 참조합니다**
  (실기 확인). 따라서 텍스트 길이를 바꾸면 뒤 오프셋이 전부 어긋나 대사가 밀리거나
  뒤섞이고 화자도 어긋납니다. **모든 `0x07`/`0x00`의 바이트 위치를 원본과 동일하게
  유지**해야 합니다.

편집 절차: 대사 섹션을 압축 해제 → 스크립트 헤더는 그대로 두고 **각 페이지를 원본 페이지의
바이트 길이에 맞춰**(한국어가 짧으면 뒤를 공백 `0x20`으로 패딩; 화면엔 안 보임) 교체하여
텍스트 영역 전체 길이와 모든 제어 코드 오프셋을 보존 → 0x08로 재압축 → (섹션 offset/length)
헤더를 갱신하며 컨테이너 재조립 → 컨테이너 엔트리를 파일 끝에 추가하고 레코드 갱신.
(`scen.rebuild_section_fit` 참고.)

## 6. 완성형(wansung) 한글 인코딩 (`culdcept/wansung.py`)

한글은 Shift-JIS에 없으므로, 필요한 한글 음절을 폰트에 이미 글리프 슬롯이 있는 **JIS
제1수준 한자 코드(0x889f~)** 에 하나씩 결정적으로 배정합니다. 그런 다음 그 슬롯에 한글
글리프를 그려 넣고(§4), 번역문을 그 SJIS 코드로 인코딩합니다. 게임은 평소처럼 코드→CMAP→
글리프 조회로 한글을 그려냅니다.

한계: 재활용한 한자 코드가 아직 번역하지 않은 화면에 나타나면 그 자리에 한글이 보입니다
(부분 패치의 알려진 특성). 한 장면을 완전히 번역하면 그 장면 안에서는 충돌이 없습니다.

## 7. 나레이션 텍스처 (양피지 가이드, `apply_narration.py`)

시작화면·튜토리얼·덱선택·배틀중단에서 나오는 양피지 가이드 나레이션은 폰트로
렌더하는 텍스트가 아니라 **3DS 네이티브 ETC1A4 텍스처**로, 시나리오 컨테이너(0x0d)
안에 헤더 없이 raw 픽셀로 저장돼 있다. 크기는 **256×64**(1~2줄)와 **256×128**(3~4줄).

- **스위즐**: PICA200 표준. 8×8 픽셀 타일이 row-major로 나열되고, 타일 안은 4×4 블록
  4개가 2×2 row-major. ETC1A4 한 블록 = 16바이트(**알파 A4 8바이트 + 색 ETC1 8바이트**).
  블록 `(bx,by)`의 알파 시작 오프셋:
  `off = TS + ((by//2)*32 + bx//2)*64 + ((bx%2)+(by%2)*2)*16` (256폭 기준, tiles-per-row=32).
- **알파(A4)**: 블록당 8바이트 = 16픽셀×4비트. 니블 순서는 column-major
  (`픽셀 i → x=i//4, y=i%4`, 저니블 먼저). 이 알파가 글자 모양, 색(ETC1)이 글자 색.
- **한글 주입**: 알파만 한글 글리프로 교체하고, 색 블록은 균일 진회색 ETC1
  (`33 33 33 00 00 00 00 00` ≈ #353535)로 채운다 → 원본과 같은 진회색 글자.
  ETC1 인코더가 필요 없다(색이 균일하므로).
- **겹침 보존**: 한 텍스처의 안 보이는 아래쪽에 다른 텍스처(예: 덱 속성 설명)가
  바이트를 공유하는 경우가 있다. **한글 잉크가 있는 행까지만** 덮고 그 아래는
  건드리지 않으면 두 텍스처가 공존한다.
- **정렬**: 게임은 화면마다 표시창 위치가 다르다(설정=풀, 배틀=중앙). 각 줄을 **원본
  일본어 잉크의 가로 중심**에 맞춰 렌더하면 잘림 없이 표시된다.
- **주입 방법**: 컨테이너를 디코드(0x0d는 게임 code.bin 기반 디코더 필요)→알파 교체→
  `0x08` 무압축으로 재인코딩(커스텀 LZMA 재압축 회피)→파일 끝에 append + 오프셋 갱신.

번역 데이터는 `narration_ko.json`(엔트리·오프셋·크기·한글 줄), 로직은
`apply_narration.py` 참고. 위치는 에뮬레이터 텍스처 덤프와 알파 블록 정확 일치로 특정한다.

## 8. 비압축(raw, type 0x00) 텍스트 섹션 주의

일부 시나리오 컨테이너 섹션은 압축(0x08) 대신 **raw(0x00)** 로 저장된다(예: 퀘스트2
1947.s2 — 제목·설명·노드명). 게임은 이를 **null(0x00) 분리 세그먼트 순서**로 읽는다
(`[제목][바로 다음=설명][노드…]`). 따라서 번역 시 세그먼트 개수·순서를 보존해야 한다.
번역문이 원문보다 짧다고 **제목을 null로 패딩하면 빈 세그먼트가 생겨** 게임이 그 다음
필드(설명)를 빈칸으로 읽는다. 길이 차이는 **맨 끝(포인터 테이블 앞)에서** 흡수하고,
제목→설명은 반드시 연속 세그먼트로 둔다.

## 9. UI 버튼 아틀라스 & ETC1 코덱 (`apply_ui_images.py`, `culdcept/etc1.py`)

메뉴·필터·커맨드 버튼은 **글자까지 통째로 그려진 텍스처**다(폰트 렌더가 아님).
나레이션(§7)과 달리 **색(ETC1)까지 다시 인코딩**해야 하므로 ETC1 인코더가 필요하다.

### 9.1 3DS ETC1 블록은 리틀엔디언

가장 중요한 함정: 3DS 는 ETC1 8바이트 블록을 표준(빅엔디언)이 아니라 **u64 리틀엔디언**
으로 저장한다 = **표준 블록의 바이트 역순**. 이걸 모르면 색이 전혀 맞지 않는다.
(정방향으로 디코드 시 덤프와 0/326 일치 → 바이트 역순 후 326/326 정확 일치.)

디코딩은 그 외엔 표준 ETC1 이다: `diff` 비트로 individual(4비트 기준색 ×2) /
differential(5비트 기준색 + 3비트 델타), `flip` 비트로 2×4 서브블록 분할 방향,
서브블록마다 3비트 밝기 테이블 + 픽셀당 2비트 인덱스.

### 9.2 포맷별 블록 크기와 오프셋

| 포맷 | 덤프 fmt | 블록 크기 | 구성 |
|---|---|---|---|
| ETC1   | 12 | 8바이트  | 색만 |
| ETC1A4 | 13 | 16바이트 | 알파 A4 8 + 색 ETC1 8 |

스위즐은 §7 과 동일(8×8 타일 row-major, 타일 안 2×2 row-major). 일반화하면:

```
off(bx,by) = TS + ((by//2)*tpr + bx//2) * (blk*4) + ((bx%2) + (by%2)*2) * blk
tpr = 가로폭//8,  blk = 16(ETC1A4) 또는 8(ETC1)
색 블록 = off + 8 (ETC1A4) / off + 0 (ETC1)
```

### 9.3 확인된 아틀라스

| 이름 | 엔트리 | 타입 | TS | 크기 | 포맷 |
|---|---|---|---|---|---|
| 타이틀/맵 세로 메뉴 | 711 | 0x0c | 0x7e28 | 128×408 | ETC1 |
| 덱 편집 카드 필터   | 608 | 0x0c | 0x20   | 256×176 | ETC1A4 |
| 배틀/맵 커맨드 버튼 | 962 | 0x0c | 0x20   | 64×696  | ETC1A4 |

셋 다 **huffman(0x08/0x0c)** 이라 `code.bin` 없이 이 저장소 툴만으로 완전 재현된다.
(962 는 헤더에 46×696 으로 적혀 있지만 저장 폭은 64 로 패딩되어 있다 → `tpr=8`.)

### 9.4 아틀라스 찾는 법 — 바이트 검색이 실패하면 RGB 근사 매칭

에뮬레이터 텍스처 덤프를 기준으로 DAT 안 위치를 찾는 두 가지 방법:

1. **알파 블록 정확 일치**(ETC1A4): 덤프 알파를 A4 로 되돌려 8바이트 시그니처를 만들고
   전 엔트리에서 바이트 검색. 나레이션(§7)은 이걸로 찾았다.
2. **RGB 근사 매칭**: 위가 실패할 때. `decode_all_blocks()` 로 엔트리의 모든 8바이트
   정렬 위치를 한꺼번에 디코드하고, 덤프의 고분산 4×4 RGB 블록과 평균절대차로 비교
   (임계값 12 정도). 배틀 커맨드 버튼(962)은 알파·바이트 검색이 **전 엔트리에서 실패**
   했지만(게임이 런타임에 더 큰 버퍼로 재배치·합성하는 것으로 보임) 이 방법으로
   `diff=0.0` 정확 일치를 찾았다. 여러 후보가 나오면 매칭 위치에서 `TS` 를 역산해
   렌더해 보고 눈으로 확인한다.

### 9.5 원문 지우고 한글 그리기

색까지 바꾸므로 "원문 잉크 제거 → 한글 렌더 → 바뀐 블록만 재인코딩" 순서로 한다.
`ui_images_ko.json` 의 `mode` 가 지우기 방식이다:

- `row_pct` — 행마다 배경색(85 퍼센타일)을 구해 **편차가 큰 픽셀만** 그 색으로 치환(2패스).
  세로 그라디언트와 배경 무늬를 보존한다. 라벨이 버튼 폭을 꽉 채워 영역 안에 깨끗한
  배경 표본이 없으면 `clean_x` 로 표본 x 구간을 따로 지정한다.
- `row_fill` — 행 전체를 배경색(중앙값)으로 덮는다. `row_pct` 로 잔상이 남는 경우에 쓴다
  (메뉴 711 이 이 경우).
- `white_only` — 어두운 버튼 위 **밝은 글자 픽셀만** 배경색으로 치환(설정/종료 버튼).

렌더 후 **원본과 다른 4×4 블록만** 재인코딩하고 나머지는 원본 바이트를 유지한다
(아이콘·테두리 손실 없음). ETC1A4 는 **색 8바이트만** 교체하고 알파는 원본을 남긴다
— 버튼 모양(알파)은 그대로 두고 글자만 바꾸는 것이라 이게 맞다.

재인코딩은 individual 모드로 flip·밝기 테이블·인덱스를 완전탐색한다. 평탄·하드엣지·
그라디언트 블록은 왕복오차 ≤ 10 이고, 한 서브블록(2×4) 안에 잉크와 배경이 **모두**
들어가는 글자 가장자리 블록만 ~20 까지 커진다 — 서브블록당 기준색이 하나뿐인 ETC1
구조의 한계이며(원본 일본어 텍스처도 같은 제약을 받는다) 화면에서는 가장자리가 약간
부드러워질 뿐이다. `python culdcept/etc1.py` 로 디코더 골든 벡터 + 유형별 왕복오차를
자체 검증할 수 있다.

### 9.6 DLC 직접 리소스 헤더와 제목 경계

`.dla/.dlb/.dld/.dlj/.dlm/.dlq` 직접 리소스의 공통 헤더에서 확인된 핵심 필드:

| 오프셋 | 크기 | 의미 |
|---:|---:|---|
| `0x04` | 4 | 전체 리소스 크기 (LE) |
| `0x08` | 1 | 리소스 종류 |
| `0x09` | 1 | 암호화/후처리 플래그 |
| `0x10` | `0x1B` | Shift-JIS 제목 + 널 패딩 (`0x10..0x2A`) |
| `0x2B` | 1 | 암호화된 페이로드 시작 오프셋 (0이면 `0x80` 대체값) |

게임의 검증 함수 `0x0027635C`는 `0x10`부터 최대 `0x1C`바이트를 Shift-JIS 검증 함수
`0x00120054`에 넘긴 뒤 `0x2B`를 별도 필드로 읽는다. 암호화 플래그가 있으면
`0x001221D8`에 `(resource + payload_offset, resource_size - payload_offset, 0)`을 넘겨
4바이트 단위로 처리한다.

따라서 제목 패치는 `0x2A`까지만 쓸 수 있고 인코딩된 제목은 널 종료를 위해 최대
26바이트여야 한다. 구형 v2.4/v2.6처럼 32바이트를 널 패딩하면 `0x2B=0x30`이 0으로
바뀐다. 52바이트 아바타에서는 `0x34 - 0x80 = 0xFFFFFFB4`로 언더플로되어 약 10억 회
루프하며 미매핑 메모리에 접근한다(이슈 #13의 `PC 0x00122204`).


## 10. 엔트리 1190 문자열 교체 시 주의 — 패딩은 널(0x00)로

1190 의 문자열은 각자 **널 종료**이고 **시작 주소(포인터)로만** 참조된다. 따라서 번역문이
원문보다 짧을 때 남는 자리는 **널로 채워야** 한다. 공백(0x20)으로 채우면 원문에 없던
내용이 문자열 뒤에 붙는다.

이게 실제로 문제를 일으킨 사례(이슈 #1): 확인 메시지는 `…？
"4+/"` 처럼 **제어코드로
끝난다**. 뒤에 공백을 붙이면 그 공백이 한 줄로 렌더돼 **예/아니오 버튼이 화면 밖으로
밀려난다**. 널로 채우면 문자열이 원문과 똑같이 제어코드에서 끝나 문제가 사라진다.
가운데 정렬 문자열이 왼쪽으로 치우치던 것도 함께 해결된다.

> 대사(시나리오) 텍스트는 반대다. 페이지가 **절대 오프셋으로 참조**되므로 공백 패딩으로
> 길이를 맞춰야 한다(§5). 즉 **1190 = 널 패딩, 시나리오 대사 = 공백 패딩**이다.

### 10.1 enum_unique 필터가 놓치는 문자열

`cardtext.enum_unique` 는 오탐(바이너리 잡음)을 걸러내려고 "일본어 글자 3자 이상"을
요구한다. 그래서 2자짜리 짧은 문자열이 빠진다 — 선택창의 '예'에 해당하는 문자열이
대표적이다('아니오' 쪽은 3자라 잡힌다). 누락분은 `cards_extra_ko.json` 에 **오프셋 기준**
으로 적어 보완한다. 필터 자체를 완화하지 않는 이유는 열거 순서가 바뀌면 `cards_ko.json`
4,666개의 인덱스가 전부 어긋나기 때문이다.

`cards_extra_ko.json` 의 각 항목에는 `len`(원문 바이트 길이)을 함께 적고, 적용 시 실제
길이와 다르면 건너뛴다. 오프셋을 잘못 적었을 때 엉뚱한 위치(예: 포인터 테이블)를
덮어써 파일을 망가뜨리는 사고를 막는 안전장치다.

### 10.2 카드 레코드 위치와 449장 전수 검증 (해결)

과거에는 덱 편집·전투 화면이 다른 카드명 사본을 읽는다고 추정했지만, 원본 카드
스프레드시트와 게임 DB를 영문 식별자로 1:1 대조해 이 추정을 폐기했다. 수집 카드의
표시 이름과 설명은 모두 **엔트리 1190의 같은 널 구분 레코드**에 있다. DLC와
0x0d/0x8d 엔트리에는 별도 카드 DB가 없다.

영문 이름 세그먼트를 기준으로 한 실제 필드 배치는 다음과 같다.

```text
[-2 표시 이름] [-1 능력] [0 영문 이름] [+1 플레이버] [+2 용어] [+3 전략]
```

레코드는 크리처 241장 → 아이템 75장 → 스펠 133장 순서다. 같은 영문 이름이 반복되는
변신용 내부 레코드는 수집 카드가 아니며, 고유 영문 이름만 남기면 정확히 449장이 된다.
`verify_cards.py`는 이 구조를 이용해 다음을 자동 검사한다.

- 원본과 패치본의 엔트리 1190 길이와 널 구분 오프셋이 모두 동일함
- 표시 이름 449/449, 능력 423/423, 플레이버 449/449, 용어 292/292,
  전략 449/449의 일본어 원문 필드가 모두 변경됨
- 변경 필드에 고정 완성형 한글 코드가 있고 영문 식별자는 보존됨
- 미번역 일본어 필드 0개, 한글 코드 없는 번역 대상 필드 0개

따라서 카드명·일부 스펠 설명이 별도 압축 사본에 남았다는 과거 문서와 이슈 답변은
잘못된 가설이다. 화면이 원문이라면 DLC 카드 문제가 아니라 본편 패치본이
`load/mods/00040000000F5700/romfs/CULDCEPT.DAT`에서 실제로 읽히는지 확인해야 한다.
세부 검수 기록은 [`CARD_AUDIT.md`](CARD_AUDIT.md)에 있다.


## 11. 0x0d / 0x8d — 커스텀 LZMA (`culdcept/lzma0d.py`)

전체 엔트리의 약 5분의 1(572개)이 이 타입이다. 오래도록 "표준 LZMA 로는 안 풀린다"고만
알려져 있었는데, 게임 실행코드를 분석해 정체를 규명했다.

### 11.1 엔트리 구조

```
[0x0d 또는 0x8d] [varint 해제크기] [2바이트 props] [4바이트 BE 초기 code] [레인지코더 스트림]
```

varint 는 부호 연장 종료비트 방식이다(게임 함수 `0x002747f8`):

```
b0,b1 을 읽어 v=(b0<<8)|b1. b0 의 최상위 비트가 0이면 거기서 끝.
아니면 v &= 0x7FFF 후 b2 를 읽어 v |= (b2&0x7F)<<15. b2 최상위 비트가 0이면 끝.
아니면 v &= 0x3FFFFF 후 b3 을 읽어 v |= b3<<22.
```

### 11.2 비트 디코더는 표준 LZMA

디컴프레서 함수는 `0x00275080`(코덱 함수 포인터 테이블 `0x39bb8c` 에 등록). 핵심부:

```
cmp   sl, #0x1000000       ; range < kTopValue → 정규화
lsr   ip, sl, #0xb         ; bound = range >> 11   (kNumBitModelTotalBits = 11)
mul   ip, r2, ip           ; bound *= prob
rsblo ip, r2, #0x800       ; prob += (2048 - prob) >> 5
addlo r2, r2, ip, lsr #5   ; (kNumMoveBits = 5)
subhs r2, r2, r2, lsr #5
```

정규화도 표준(`range <<= 8; code = (code<<8) | *src++`). 다만 **초기화가 다르다** —
표준 LZMA 는 5바이트(첫 바이트 무시 + 4바이트)를 읽지만 이 구현은 **2바이트를 건너뛰고
4바이트를 빅엔디언으로** 읽는다(`range = 0xFFFFFFFF`).

리터럴 컨텍스트는 `prevByte >> 5`(lc=3, lp=0), posState 는 출력 위치의 하위 2비트(pb=2)로
표준 기본값과 같다. 그런데도 **표준 LZMA 라이브러리로는 풀리지 않는다** — props 값을
0~224 전수 대입해도 실패한다. 심볼(길이·거리) 구조가 표준과 다르기 때문이다.

### 11.3 그래서 에뮬레이션으로 푼다

가장 확실한 방법은 게임 코드를 그대로 실행하는 것이다. `culdcept/lzma0d.py` 가 Unicorn 으로
`0x00275080` 을 호출한다.

- 인자: `r0` = `{u32 src; u32 src_end; u32 refill_fn;}` 구조체, `r1` = 출력 버퍼
- s0/s1 을 스크래치로 쓰므로 **VFP 를 켜야** 한다
- code.bin 매핑은 한 번만 하고 인스턴스를 재사용하면 빠르다(엔트리당 수십 ms)

검증: 572개 전부 오류 없이 해제되고, 나레이션 엔트리는 배포본(0x08 로 변환해 둔 것)과
선두부터 완전 일치한다.

### 11.4 주의 — 해제 크기와 텍스처가 어긋나는 엔트리

일부 엔트리(1595·1596·1601)는 나레이션 텍스처의 뒷부분이 **해제 결과의 끝을 넘어간다**.
어차피 주입할 때 `0x08` 무압축으로 다시 쓰므로, 필요한 만큼 0 으로 늘려두면 게임이 그
크기 그대로 읽어 문제가 없다(`apply_narration.py` 가 자동으로 처리).

`code.bin` 은 저작권상 배포하지 않는다. 본인 롬에서 `extract_code.py` 로 추출한다
(NCSD → NCCH → ExeFS `.code` → BLZ 해제).


## 12. ★패딩은 반드시 공백(0x20) — 널을 채우면 안 된다

번역문이 원문보다 짧을 때 남는 자리를 무엇으로 채우느냐가 **매우 중요하다**.
반드시 **공백(0x20)** 으로 채워 원본의 널 개수를 그대로 유지해야 한다.

### 왜인가

게임은 다음 데이터를 **널로 구분된 세그먼트 순서**로 읽는다.

* 카드 레코드 — `[설명][이름][능력치][영문명][플레이버]`
* 퀘스트 데이터 — `[제목][설명][노드명…]`

널을 하나라도 더 넣으면 **빈 세그먼트가 새로 생겨** 그 뒤 필드가 전부 밀린다.
화면에서는 카드 설명이 **비어 보이고**, 퀘스트는 설명·노드 이름이 어긋난다.

실제로 v1.9 에서 이 실수를 저질렀다(이슈 #3).

| | 원본 | v1.9~v2.0 |
|---|---|---|
| 엔트리 1190 빈 세그먼트 | 4,396 | 25,423 |
| 퀘스트 1947.r2 세그먼트 | 39 (빈 17) | 47 (빈 25) |

### 그런데 제어코드로 끝나는 문자열은?

확인 메시지처럼 `…？
<제어코드>4+/` 로 끝나는 문자열은 **뒤에 뭔가를 붙이면**
(공백이든 널이든) 화면에 한 줄이 더 생겨 예/아니오 버튼을 밀어낸다(이슈 #1).

그래서 `apply_korean_full.py` 의 `pad_fill()` 은 **제어코드 앞쪽에** 공백을 채운다.
길이는 맞추면서 문자열은 원문처럼 제어코드로 끝나므로 두 문제가 함께 해결된다.

### 자동 검사

`check_structure.py` 가 이 불변식을 검사한다. 빌드 후 반드시 한 번 돌릴 것.

```bash
python check_structure.py 원본.DAT 패치본.DAT
```


## 13. DLC 리소스 파일 (.dla/.dlb/.dld/.dlj/.dlm/.dlq)

DLC 콘텐츠(`0004008c000f5700`)의 각 `.app` RomFS 안에 들어 있는 파일이다.

```
0x00 u32 LE  무결성 값 = zlib CRC-32
0x04 u32 LE  파일 크기
0x08 u32 LE  종류 ID (0x101~0x114)
0x09 u8      암호화 플래그 (위 u32 의 두 번째 바이트)
0x10~        Shift-JIS 제목, NUL 종료, 실질 26바이트
0x2B u8      페이로드 시작 오프셋 (0 이면 0x80 — .dlm 이 여기 해당)
페이로드     LCG 스트림 암호
```

### 무결성 값 (★ 이걸 몰라서 오래 헤맸다)

게임은 CRC 를 계산하기 **전에** 두 가지를 먼저 한다.

1. 페이로드를 LCG 로 복호화한다 — `x = (x*5 + 0x35733573) & 0xFFFFFFFF`, seed 0,
   32비트 LE 워드 단위로 `plain = cipher - x`
2. 헤더 바이트 `0x09`(암호화 플래그)를 **0 으로 지운다**

그 상태의 버퍼에 `zlib.crc32(buf[4:size])` 를 걸어 `u32@0x00` 과 비교한다.
불일치하면 검증기가 -3 을 반환하고 게임은 그 리소스를 버린다. 리소스를 하나라도
거부하면 **DLC 가 통째로 사라진 것처럼** 보인다.

원본 바이트에 그냥 CRC32 를 돌리면 절대 맞지 않는다 — 이 전처리 두 가지 때문이다.
표준 체크섬을 아무리 시도해도 안 맞아서 "무결성 값이 아니다"라고 오판하기 쉽다.

### 제목 검사

제목은 별도의 Shift-JIS 구조 검사기(vaddr `0x00120050`)를 통과해야 한다.

* 단바이트: `0x20`~`0x7F`
* 2바이트: 선두 `0x81~0x9F` 또는 `0xE0~0xFC`, 후속 `0x40~0xFC`(`0x7F` 제외)
* NUL 까지 누적 28바이트 미만 → 전각 기준 최대 13글자

완성형 매핑이 쓰는 한자 슬롯(`0x889F~0x9872`)은 이 검사를 그대로 통과한다.
즉 **한글이라서 거부된 것이 아니다** — 유효한 일본어로 바꿔도 똑같이 거부된다.
문제는 언제나 CRC 였다.

### 페이로드 내용

복호화하면 게임 자체 포맷이 나온다.

* `.dld`/`.dlj`/`.dla`/`.dlb` — 널 종료 SJIS 문자열(이름·설명)이 그대로 들어 있다
* `.dlm`/`.dlq` — `(offset, length)` 섹션 컨테이너. 각 섹션은 0x08/0x0c 코덱으로
  압축돼 있고 안에 맵 지형명·시나리오 제목·에피소드명·대사가 있다.
  섹션 사이에 여유 공간이 **1바이트도 없고** 파일 크기도 바꿀 수 없으므로,
  압축 섹션을 고치려면 재압축 결과가 원본 크기 이하여야 한다.

### 코드 위치

`update_code.bin`(ver 1.2) 기준: 검증기 `0x002764d0`, LCG `0x0026d41c`,
CRC `0x0026e2cc`, 제목 검사기 `0x00120050`.

## 14. ★대화창은 20칸이고 폰트는 고정폭 — 채움은 전각 공백으로

이 두 사실이 같이 걸리면 **빈 대화창**이 생긴다. 이슈 #24 에서 한 번, #29 에서 또 한 번
같은 자리를 밟았다.

### 고정폭이라는 뜻

대사 폰트는 고정폭이다. 한자·가나·한글(모두 2바이트)이 한 칸을 차지하는데,
**반각 공백(1바이트)도 똑같이 한 칸**을 차지한다. 즉 화면 폭은 바이트 수가 아니라
**글자 수**로 정해진다.

### 대화창은 20칸

원본 대사 줄의 폭을 전수로 세면 20칸에서 정확히 끊긴다.

    본편  …19칸 4,384줄 → 20칸 2,851줄 → 21칸 233줄 (급감)
    DLC   최대 20칸, 21칸 이상 0줄

21칸 이상은 전부 카드 설명문·능력 설명처럼 게임이 알아서 줄을 바꿔 주는 패널의
문자열이다. 대사 페이지는 20칸을 넘지 않는다.

### 그래서 채움은 전각 공백(0x8140)

번역문은 원본 페이지의 **바이트 길이**를 지켜야 한다(게임이 페이지 0x07·문자열 0x00
위치를 그대로 참조한다). 예전 코드는 남는 자리를 반각 공백으로 채웠는데,

    원문 줄  40바이트 = 20칸
    한글 줄  30바이트 = 16칸   (공백·문장부호가 1바이트라 바이트당 칸이 많다)
    반각 10개 채움 →  16 + 10 = 26칸  →  대화창을 넘어 줄바꿈 → 페이지가 밀림

전각 공백은 2바이트에 한 칸이라 원문과 밀도가 같다.

    전각 5개 채움 →  16 + 5 = 21칸

0x8140 은 한글이 빌려 쓰는 슬롯(0x889f~0x9872) 밖이라 폰트에 원래 빈칸 그대로 남아
있다. 구현은 `culdcept/pagepad.py` — 어느 줄에 넣을지는 **그때그때 가장 짧은 줄**에
한 칸씩 주어, 가장 넓은 줄의 폭이 최소가 되게 한다.

## 15. ★번역 안 된 한자는 "깨진 한글"로 보인다 (`find_garbled.py`)

한글을 JIS 제1수준 한자 슬롯에 얹어 쓰기 때문에, 번역이 안 된 채 남은 그 구간 한자는
화면에 엉뚱한 한글로 그려진다.

    位 → 겁     戦 → 쟁     勝 → 쐴     枚 → 흡     取 → 쇠     能 → 퓰

일본어로 남으면 눈에 띄지만 이건 한글처럼 보여서 그냥 오타로 오해받는다(이슈 #29의
"4겁 유마", "1쟁 1쐴"). 게다가 "쟁"으로 원문을 찾아도 안 나온다.

슬롯 경계도 알아 두면 좋다. 폰트의 한자 슬롯은 2,965개인데 한글은 2,350자만 쓰므로,
**0x94fc 를 넘는 코드의 한자는 덮이지 않고 원래 한자 그대로 그려진다.** 그래서 미번역
일본어는 "깨진 한글 + 멀쩡한 한자 + 가나"가 섞여 보인다.

    セプター能力を取り戻して  →  セプター퓰力を쇠り戻して
              (能 0x945c → 퓰, 取 0x8ee6 → 쇠, 力 0x97cd·戻 0x96df 는 경계 밖이라 그대로)

찾는 법: 번역된 문자열에는 그 자리에 진짜 한글이 들어 있으니, **패치본과 원본이 완전히
같으면서** 그 구간 코드를 담은 문자열이 곧 깨져 보일 후보다. `find_garbled.py` 가 한다.
