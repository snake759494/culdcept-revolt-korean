# 지켜야 할 규칙 — 고친 것이 다시 망가지지 않게

이 프로젝트에서 **같은 자리를 여러 번 고쳤다가 다른 곳을 망가뜨린** 일이 반복됐다.
아래는 그때마다 확인한 사실과, 다시는 어기지 말아야 할 규칙이다. 새 수정을 넣기
전에 이 문서를 먼저 읽고, 마지막 절의 검사를 **반드시** 돌린다.

---

## 1. 카드 이름 필드는 **채우지 않는다**

원본 카드 표시 이름 510개 중 채움(공백·제어코드)이 붙은 것은 **하나도 없다.**
번역이 짧다고 뒤를 채우면 어느 쪽으로 채워도 탈이 났다.

| 채움 | 결과 |
|---|---|
| 공백 `0x20` | 고정폭이라 한 칸을 그대로 먹는다. 이름이 배너에 끼워 넣어져 `ロア의파이어드레이크␣␣␣␣` 가 배너를 넘기고 **ＳＴ/ＨＰ 변환 줄이 화면 밖으로 밀렸다.** |
| 폭 0 제어코드 `0x08 @` | 배너는 멀쩡해지지만 **손패 목록이 깨진다** — 이름이 통째로 사라지거나, 색이 다음 줄까지 번지거나, 글자가 깨진다. 목록 아래로 갈수록 심해진다. |

**규칙**: 이름은 번역한 만큼만 쓰고, 남는 바이트는 **바로 뒤 필드(능력)의 꼬리
공백**으로 넘긴다(`culdcept.cardtext.rebalance_names`). 널 개수와 레코드 전체
길이는 그대로 둔다. 본편 DAT(`apply_korean_full.py`)과 업데이트 실행코드
(`apply_update_code.py`) **양쪽에 똑같이** 적용한다.

## 2. 문자열이 **줄바꿈 + 제어코드**로 끝나면 채움을 그 앞에 넣는다

뒤에 붙이면 그 공백이 한 줄로 렌더돼 버튼을 밀어낸다 —
"이 크리처를 소환하시겠습니까?" 밑의 **「아니오」가 화면 밖으로 밀렸다.**
`pad_fill()` 이 이 처리를 한다. v2.24 에서 이름 채움을 넣으며 이 처리가 사라져
증상이 되살아났다. **`pad_fill` 을 고칠 때 이 분기를 지우지 마라.**

## 3. 널(0x00)로 채우지 않는다

카드 레코드와 퀘스트 데이터는 널로 구분된 필드를 **순서대로 세면서** 읽는다.
널이 하나 늘면 뒤 필드가 전부 밀려 설명문이 통째로 비어 버린다.
예외: 엔트리 1190 **s3** 의 짧은 라벨은 오프셋 참조라 널 채움이 안전하다.

## 4. 이름 자리 표기 `{N}` 을 아는 인코더로만 넣는다

`dialogue_ko.json` 은 주인공 이름 자리를 `{N}` 으로 적는다(1,008곳).
이걸 모르는 인코더에 넣으면 화면에 **글자 그대로 `{N}`** 이 나온다.
실제로 `apply_update_scenario.py` 가 `cardtext.encode` 를 쓰면서 실행코드 쪽
대사에 리터럴이 들어갔다. 지금은 `cardtext.encode` 와 `dlctext.encode` 가
모두 `{N}` 을 3바이트 제어코드(`03 30 2F`)로 바꾼다. **새 인코더를 만들면
반드시 같은 처리를 넣는다.**

## 5. 번역이 자리보다 길면 **빌더가 공백을 지운다** — 먼저 재 봐라

페이지 바이트 수는 원문 길이로 고정이다. 넘치면 빌더가 뒤에서부터 공백을 지워
`조금…… 강하게 해 볼게.` 가 `조금……강하게해볼게.` 로 나온다.

* 자리는 **섹션(끝 영역) 전체**에서 페이지끼리 빌려 준다(`spread_budgets`).
  이벤트 경계는 옮겨도 된다 — 끝 영역은 널로 구분된 이벤트를 순서대로 읽고,
  이벤트는 바이트 위치가 아니라 색인으로 참조된다.
* `missed_ko.json` 의 오프셋 기준 세그먼트는 **서로 빌릴 수 없다.** 자리가
  모자라면 문장을 줄이는 수밖에 없다.
* 빌드는 한 시간이 걸린다. 번역을 고칠 때마다 **`여유검사.py`** 를 돌려
  `자리가 모자란 페이지 0곳` 인지 확인한다.

## 6. 대화창은 20칸 × 3줄로 본다(실측은 22칸)

`pagepad.BOX=20` 은 일부러 보수적으로 잡은 값이다. 이름 치환(`{N}`)이 0칸으로
계산되므로 긴 이름에서는 실측 22칸을 넘길 여지가 남는다. **넓히지 마라.**

## 7. 엔트리는 **제자리**에 둔다

원래 크기에 안 들어가 파일 끝으로 밀리면 옛 바이트가 그 자리에 남아 게임이
그쪽을 읽는 일이 있었다. 밀어낼 때는 옛 자리를 0으로 지운다.
`pack()` 에는 **반드시 예산을 넘긴다**(안 넘기면 원래 코덱으로만 눌러 보고 만다).

## 8. 화면에 나오는 카드·시나리오 텍스트는 **업데이트 실행코드에도** 있다

게임 업데이트(ver 1.2)를 깔면 게임은 카드 이름·능력과 일부 시나리오·전투 대사를
`CULDCEPT.DAT` 이 아니라 **실행코드 사본**에서 읽는다. 사본은 4개다.

| 위치 | 내용 |
|---|---|
| `+3,333,684` | 전투 중 캐릭터 대사 (엔트리 1869) |
| `+3,338,152` | 전투 중 캐릭터 대사 (엔트리 1870) |
| `+3,342,732` | 시나리오 (엔트리 1947 섹션 3) |
| `+3,348,324` | 시나리오 (엔트리 1949 섹션 6) |
| `0x308578~` | 카드 DB (엔트리 1190 섹션 0) |

**규칙**: `cards_ko.json`·`dialogue_ko.json`·`block_ko.json` 을 고쳤으면
**`apply_update_code.py` 와 `apply_update_scenario.py` 를 반드시 다시 돌린다.**
이걸 빠뜨려 실행코드가 v2.17 무렵 번역으로 굳은 채 여러 판이 나갔고,
카드 오타 수정이 화면에 전혀 나오지 않았다.

## 9. "파일에 한글이 있다" ≠ "화면에 한글이 나온다"

이 문장을 여러 번 틀렸다. 배포 전에 **빌드 결과 파일의 실제 바이트**를 확인한다
(`화면문장확인.py`). 그래도 화면 확인이 아니라는 점을 답변에 밝힌다.

---

## 배포 전 검사 (전부 통과해야 한다)

```bash
python 여유검사.py <원본 CULDCEPT.DAT>          # 자리가 모자란 페이지 0곳
python 배포전검사.py <원본 CULDCEPT.DAT> <빌드한.DAT> [--code <빌드한 code.bin>]
python verify_cards.py <원본 CULDCEPT.DAT> <빌드한.DAT>
```

`배포전검사.py` 가 위 규칙을 기계로 확인한다 — 카드 이름에 제어코드·꼬리 공백이
없는지, 널 개수가 그대로인지, 리터럴 `{N}` 이 남지 않았는지, 엔트리가 제자리인지,
옛 바이트가 남지 않았는지.
